# GitHub Copilot Pilot — Discussion Questions

## Core Questions

1. Workflow: Can you walk me through how code goes from my computer to a working client demo, including where things tend to go wrong?
2. Code review: With Copilot making it easier to produce code quickly, how do we make sure we can review and trust what it produces without slowing the team down?
3. Best practices: Given that we have two junior developers and limited time, what practices should we establish now to avoid creating problems for ourselves later?
4. Deployment and access: What systems do we need access to, who controls that access, and what determines where our code can run?
5. Cost and scaling: What costs or limitations should we understand now, and what would become a problem if we expanded this approach to more developers or larger projects?

## Fallback Questions

Use these if someone has already covered a similar topic or the conversation moves in a different direction.

1. Avoiding rework: What's a mistake teams make early on that ends up costing them a lot more time later?
2. Getting value from AI: Where does Copilot genuinely save time, and where does it sometimes create more work than it saves?
3. Knowing when code is good enough: How do you decide when something is good enough for a client demo versus when it needs more work?
4. Managing risk: What's the kind of problem that's easy to miss in a demo but could become a serious issue if we built on top of it?
5. Using senior developers effectively: What's the best way for junior developers to use your time when we're stuck, so we learn without creating unnecessary bottlenecks?
6. Knowing what to automate: How do we know when a process is worth automating, rather than just doing it manually?
7. Keeping projects maintainable: What are the signs that we're building something in a way that'll make it difficult to change later?
8. Demonstrating value: How can we tell whether we're making real progress for the client, rather than just producing more code?
9. Learning from the pilot: If we wanted to use what we learn here to improve how other teams work, what would be the most important lessons to capture?
10. Prioritizing improvements: If you had just one hour to improve how our team develops software, what would you spend it on?

## Useful Follow-Up Prompts

When the developer mentions something interesting, ask:

- Why does that happen?
- How do you handle that today?
- What would you recommend for a team at our stage?
- What would be the first sign that we need to improve our approach?

## Guiding Principle

Focus on practical problems, lessons learned, and decisions that save time or reduce risk. Ask questions that invite real examples rather than technical explanations for their own sake.
